# 0003. Действия через карточки подтверждения и машиночитаемые ошибки

## Статус

Принято (этап 3, 25.11.2026)

## Контекст

Прошлые этапы научили читать данные абонента и базу знаний. Осталось
менять данные: смена тарифа, услуги, контакты — и эскалация в поддержку.
Требования этапа: модель не исполняет изменения сама (только готовит и
пересказывает карточку, исполнение — за кодом после явного «да»); ошибки
валидации доходят до модели машиночитаемо, чтобы она исправила вызов;
повторное «да» не создаёт второго эффекта; субъект действия пока приходит
аргументом `sub` (осознанная дыра, JWT закроет её на этапе 5).

## Решение

1. **Контракты (`actions/contracts.py`)**. `ActionError(code, message,
   **hints)` с `to_tool_result()` → `{"error", "detail", **hints}`;
   `BUSINESS_RULE_CODES` (same_tariff, tariff_not_available,
   service_already_on/off, same_contacts) — повторять бессмысленно,
   модель пересказывает отказ. Нормализация «как услышали» → точное
   значение каталога (unknown_tariff отдаёт `available`).
2. **Слой действий (`actions/service.py`)**. Три `prepare_*` проверяют
   предусловия и собирают `view` карточки, не исполняя; `execute_action`
   (только для кода оркестратора) ходит в REST-моки: тариф — в биллинг с
   `idempotency_key`, услуги и контакты — в CRM. Все исходы приведены к
   executed / duplicate / daily_limit / отказам.
3. **Action-MCP (`actions/server.py`)**. Один MCP-сервер без auth на
   `Mount("/actions", streamable_http_app())`, lifespan запускает
   session manager (приём стенда). `ActionError` → `MCPError(-32002,
   message=code, data=to_tool_result)` — подсказки едут до модели.
4. **Идемпотентность (`app/idempotency.py`)**. `execute(key, sub, action,
   fn)`: ключ найден — duplicate без исполнения; неудачный исход ключ не
   занимает (сбой не запирает повтор); успех — `INSERT ... ON CONFLICT DO
   NOTHING`. Ключ оркестратора: `f"{action}:{pending_id}"`.
   Нюанс: биллинг держит свою дедупликацию в той же таблице под тем же
   ключом, поэтому признак «мой повтор» — проверка ключа *до* исполнения,
   а не факт вставки.
5. **Карточка в контуре чата**. Обёртка (`app/wrap.py`) подставляет
   `session.user.sub` (пока он в схеме) и на успешный `prepare_*` создаёт
   карточку через готовый `app/cards.py`; модель получает «перескажи
   карточку, спроси да/нет». Оркестратор классифицирует следующую реплику
   кодом (`app/cards.py::classify_answer`): «да» → исполнение, «нет» →
   отмена, «оператор» → тикет + отмена, смена темы → обычный ход, карточка
   живёт. Кнопки карточки — `POST /api/cards/{pending_id}/decision`.
6. **Агенты (`app/workers.py`)**. Тарифный агент (три prepare_* + read) и
   агент эскалации (create_ticket); `execute_action` в наборы агентов не
   отдаётся никогда. У тарифного агента запасной промпт на случай, когда
   prepare недоступен (барьер прав, этап 4).

## Последствия

- Положительные: три класса исходов разведены (валидация → модель
  исправляет вызов; бизнес-отказ → пересказ; сбой → клиентский повтор);
  повтор «да» отдаёт «Эта операция уже исполнена — повтор не выполнялся.»
  и не трогает моки; для тарифа два барьера идемпотентности
  (оркестратор + биллинг).
- Отрицательные: `sub` в аргументах — дыра до этапа 5 (тогда уберём из
  контрактов, субъект из JWT); smoke-группа 2 вызывает инструменты без
  `sub` — она намеренно красная до этапа 5 и станет зелёной с ним.
- Компромисс: слабые локальные модели игнорируют инструкции, поэтому
  оркестратор дублирует императив вызова `prepare_*` текстом задачи шага
  (action=true) — для сильных моделей это избыточно, но безвредно.
