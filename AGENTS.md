# AGENTS.md — контекст и правила проекта

Этот файл — постоянная память проекта. Ассистент поддерживает его в актуальном
состоянии на протяжении всего проекта: фиксирует здесь способ чтения PDF,
находки из логов автотестов и прогресс по этапам.

## О проекте

- Учебный проект Хекслета (`llm-developer-project-445`): AI-оператор для сайта
  мобильного оператора связи. Цель — разобраться в структуре работы с локальными
  LLM: оркестрация агентов на OpenAI Agents SDK, MCP-серверы с JWT, контракты
  действий с идемпотентностью, журнал аудита, права через политики Dogwood,
  guardrail-сервис.
- Проект состоит из **10 этапов**. Каждый этап описан в отдельном PDF-файле.
- Заготовка кода: репозиторий
  [hexlet-components/projects-llm-telecom-operator-agent](https://github.com/hexlet-components/projects-llm-telecom-operator-agent).
  Код студента помечен `TODO(<тема>)` в `app/`, `actions/`, `guardrail/`,
  `pdp/policies/tariff.dw`; готовое (`core/`, `services/`, `stand.py`, `web/`,
  `tests/smoke.py`) не менять. `tests/smoke.py` — исполняемая спецификация:
  группы 0–5 по шагам, 54 проверки, без LLM. Цели Makefile не переименовывать:
  автопроверка использует `make setup`, `make stand`, `make api`,
  `make actions`, `make pdp`, `make guardrail`.
- Критерий успешного прохождения этапа — **прохождение скрытых автотестов
  куратора**.

## Проверка результатов (автотесты)

- Автотесты в репозитории не видны. Они запускаются на каждый `git push` через
  workflow `.github/workflows/hexlet-check.yml` (`hexlet/project-action`).
  Этот файл нельзя удалять, редактировать, переименовывать; репозиторий нельзя
  переименовывать.
- О том, пройден ли этап, узнаём **после `git push` по логам workflow** в
  GitHub Actions. Логи пользователь присылает в чат, либо ассистент получает их
  самостоятельно через `gh`.
- После прохождения первого этапа проверить логи на предмет расположения
  автотестов и эталонного решения. Найденное зафиксировать в разделе
  «Находки из логов».

### Команды для получения логов

```bash
gh run list --limit 5          # последние запуски workflow
gh run view <run-id> --log     # логи конкретного запуска
gh run view --log-failed       # только упавшие шаги последнего запуска
gh run watch                   # следить за текущим запуском
```

## Работа с PDF-спецификациями

1. Пользователь присылает PDF, описывающий этап.
2. Ассистент нумерует файл в формате `NN_оригинальное-имя.pdf`
   (`01_...`, `02_...`, ...) и сохраняет в папку `specification/`.
3. Ассистент читает PDF и составляет план решения этапа (список шагов).
4. План согласуется с пользователем, далее работа идёт по шагам.

### Способ чтения PDF

Зафиксировать здесь после **первого успешного чтения** PDF, чтобы не перебирать
варианты каждый раз.

Проверено на PDF этапа 1 (24.11.2026):

- Инструмент `Read` PDF **не читает** («not readable as UTF-8 text»).
- Рабочий способ — `pdftotext` (poppler, есть в Git Bash):
  `pdftotext -layout -enc UTF-8 "<pdf>" /tmp/stageN.txt`, затем `Read` файла.
  Флаг `-enc UTF-8` обязателен: без него вывод в ISO-8859 и `Read` отказывает.
- Запасной способ — `pypdf` 6.19.0 (Python 3.14): `page.extract_text()`,
  удобен для построчного поиска по ключевым словам.
- Особенности вёрстки: длинные строки код-блоков в PDF **обрезаны** (снимок
  скроллящегося блока с сайта) — восстанавливать по смыслу и по README
  репозитория заготовки; двухколоночная вёрстка местами сдвигает строки.

## Правила работы ассистента

1. Ассистент **не вносит правки в код самостоятельно**. Единственный файл,
   который ассистент редактирует сам, — этот `AGENTS.md`.
2. Весь код ассистент предоставляет **в чате** с точным указанием, в какой файл
   и в какое место его добавить (включая содержимое ADR — их пользователь
   сохраняет сам).
3. На каждом шаге этапа ассистент кратко объясняет, что нужно сделать.
4. Ассистент **не переходит к следующему шагу**, пока пользователь явно не
   подтвердил завершение предыдущего.
5. Тесты: ассистент сообщает, **как их запустить** и **какой результат ожидать**.
6. После завершения этапа — `git push` и анализ логов workflow (см. выше).

## Требования к коду

- Каждая функция содержит **докстринг**.
- Запрещены однобуквенные имена переменных и обобщённые имена вроде `item`,
  `row`, `data` — имя должно отражать смысл значения.

## ADR (Architecture Decision Records)

- Перед завершением каждого этапа (когда пройдены все задачи из PDF) ассистент
  составляет ADR. Текст ADR ассистент выдаёт в чате, пользователь сохраняет его
  в папку `docs/adr/`.
- Имя файла: `NNNN-kratkoe-nazvanie.md` (например,
  `0001-arhitektura-agenta.md`).
- Формат (на русском): **Статус**, **Контекст**, **Решение**, **Последствия**.
